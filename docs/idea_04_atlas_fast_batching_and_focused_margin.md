## 1. 背景と解決すべき課題（なぜ試す価値があるか）

Discussion [Topic 753177] のゼロ重みアブレーション（Zero-weight ablation）実験において、各モジュールを抜いた際の Public LB 低下幅が以下のように報告されています：
* **Prompt-Centered Twins（両方除去）**: `-0.017`
* **ATLAS（ソース条件付き尤度）除去**: **`-0.009`（単一後処理モジュールとして最大級の寄与）**
* **Soft Sinkhorn 除去**: `-0.002`

ATLAS は Qwen3-8B ベースモデル（`B8`）に各モデルの条件付きアダプタ/プロンプトを与え、テスト文章のトークン単位の生成尤度（Log-Likelihood）を直接計算する強力なモジュールですが、**計算コストが非常に重く、残り時間（`ATLAS_BUDGET`）が尽きた時点で未評価の行を残して途中終了する設計** になっています。

直近のコード比較により、現行の V40 / V43（および 0.668 基準版）の ATLAS 設定には、**スループットと対象行選択の効率において改善の余地がある** ことが判明しました。

## 2. 提案手法の技術仕様（3つの改善点）

| パラメータ | 現行設定 (V40 / 0.668基準) | 提案設定 (Apex Aegis 方式) | 技術的メカニズムと変更理由 |
| :--- | :---: | :---: | :--- |
| **`--atlas_bs`** | `4` | **`6`** | Shortest-first（文字数順ソート）パディング下では BS=6 でも T4 VRAM（16GB）に余裕で収まり、**GPU スループットが約 30〜35% 向上** する |
| **`--atlas_margin`** | `0.32` | **`0.28`** | Top-1 と Top-2 の確率差が `0.28〜0.32` の「ほぼ勝敗が決している行」への冗長な ATLAS 計算を省き（約30%削減）、**本当に競っている難所ペアに計算予算を 100% 集中** させる |
| **Pairwise Gate & Weight** | `margin < 0.35`, `w = 0.10` | **`margin < 0.36`, `w = 0.115`** | `v34_pairwise.py`（Evidence-Aware A/B Verifier）の適用範囲を僅かに広げ、重みを +15% 強化して双子モデルのタイブレーク力を高める |

### 数理仕様：Dispute Gate の役割分担

一次アンサンブルの事後確率を $P_{\text{base}}(y \mid x)$ とし、上位 2 クラスのマージンを $M(x) = P_{(1)}(x) - P_{(2)}(x)$ と定義します：

1. **$M(x) < 0.36$（中〜強度の競合行）**:
   軽量（実行時間 16 秒）な `V34.1 Pairwise Verifier` の対数確率 $\log P_{\text{pair}}(x)$ をゲート強度 $g(x) = \text{clip}\left(\frac{0.36 - M(x)}{0.36}, 0, 1\right)$、重み $0.115$ で加算。
2. **$M(x) < 0.28$（最難関の競合行）**:
   重量級の `ATLAS` トークン尤度計算を `BS=6` で高速実行し、重み $0.20$ でブレンド。

## 3. 期待されるメリット

* **時間切れによる「ATLAS 途中打ち切り（未評価行の発生）」の完全回避**:
  `BS=6` による 35% 高速化と `margin=0.28` による対象行 30% 絞り込みの相乗効果により、ATLAS フェーズの所要時間が大幅に短縮されます。これにより、Kaggle GPU セッションの個体差（遅い T4 個体を引き当てた場合）でも、全対象行を確実に最後までスコア付けできるようになります。
* **9 時間 VOID 崖に対する圧倒的な安全性（Global Watchdog）**:
  全体の実行時間が約 5.0〜5.5 時間に収まるため、9 時間タイムアウトに対して **3.5 時間以上の安全マージン** を確保できます。

## 4. 導入に伴うリスク・デメリット・制約事項

> [!NOTE]
> **マージン縮小（0.32 $\to$ 0.28）による境界サンプルの取りこぼし懸念**

1. **マージン `0.28 〜 0.32` 領域のサンプルに対する影響**:
   * もし一次アンサンブルが「マージン `0.30` のやや高い確信度で間違えている（Overconfident Error）」サンプルが存在した場合、`atlas_margin` を `0.32` から `0.28` に下げると、そのサンプルは ATLAS による再評価（逆転救済）を受けられなくなります。
2. **緩和策**:
   * `BS=6` に引き上げたことで既にスループットが 35% 向上しているため、もし計算時間に十分な余裕がある場合は、`--atlas_bs 6` だけを採用して **`--atlas_margin 0.32`（または `0.30`）を維持する** ことで、「高速化」と「広い救済範囲」の両取りが可能と考えられます。
