# Strategic Verification & Breakthrough Plan (2026-11-13)

本計画は、E1/E2 アブレーション実験の確定結果（`0.677` / `0.676`）および Kaggle 公開領域で共有された最新の検証知見（公開 `0.684` 構成、同一コード LB ノイズ幅最大 `0.009`、2-answers/prompt 検証相関 `0.91`）を客観的に評価し、限られた提出枠（1日 5 回）と 2×T4 実行時間制限（上限 9 時間）の中でメダル圏（Bronze `0.683` / Silver `0.684`）および上位層（`0.70+`）を目指すための実行計画です。

---

## 1. 現状の客観的評価（Evidence-Based Assessment）

### 1.1 確定している技術的事実
1. **LB のノイズ構造（最重要リスク）**:
   - 同一コードを再提出しても、Public LB スコアは最大 **`0.009`** 程度変動することが実測されています（コミュニティ実測例: `0.643 vs 0.651`、我々の実測: V56-Fix `0.675〜0.680`）。
   - したがって、1 回の LB 提出における `±0.003〜0.005` の差のみを根拠に「改善／悪化」を断定することは統計的に危険であり、**ローカルでの信頼性の高い検証指標**が不可欠です。
2. **OOF と LB の乖離原因と解決策**:
   - 従来のローカル OOF は「1 プロンプトにつき全 18 モデルの回答」を含めて評価していたため、LB との相関係数が **`0.13`** に留まっていました。
   - 隠れテストセットでは「1 プロンプトにつき少数の回答（2 回答程度）」しか含まれないため、**「1 プロンプト＝2 回答のみをランダムサンプリングするモンテカルロ OOF」** へ切り替えることで、LB との相関が **`0.91`** へ改善することが報告されています。
3. **V58 / V59 (`0.673`) 低下の原因とベースラインの健全性**:
   - E1（GSQ `0.06` 単独 = `0.677`）および E2（ATLAS `0.15` 単独 = `0.676`）ともに悪化せず、V56-Fix 系列（`Qwen3 0.40 + WeMM 0.07 + 親スタック 0.53`）の安定性が再確認されました。
   - V58 / V59 の低下は、リークを含む誤った OOF 指標によって Qwen3 比率を `0.50` へ引き上げ、親アンサンブルの多様性を損なったことが主因と考えられます。
4. **公開 `0.684` レシピとのギャップ**:
   - 現在の公開 SOTA（`0.684`）は、`WeMM-4B`、タイポグラフィ証拠/ペナルティ、兄弟残差を含まない、よりシンプルな 6 メンバー＋Qwen3-Embedding (`0.40`)＋GSQ (`0.03`)＋`comp_stack` (`0.15`)＋Sinkhorn (`0.30`) で達成されています。
   - ただし、公開ウェイトの単純なブレンド調整だけでは `0.680〜0.684` の過密ゾーン（ノイズ圏）から抜け出すことは困難と推測されます。

## 2. 段階的アクションプラン（Phased Execution Plan）

### Phase 1: 検証プロトコルの刷新（ローカル / Colab・提出枠消費なし）
**目的**: 1 回の LB 提出（6時間 + 1枠消費）に依存せず、事前に LB 転移性を高精度（目標相関 > 0.85）で判定する環境を構築する。

- **タスク 1-1: 2-Passage Sparse Sampling OOF の標準化**
  - ワークスペースの [`eval_sparse_sampling_harness.py`](file:///Users/echo/kaggle/name-that-llm/eval_sparse_sampling_harness.py) および Colab 検証ノートブック [`v58_v59_root_cause_and_apex_restoration.ipynb`](file:///Users/echo/kaggle/name-that-llm/colab/v58_v59_root_cause_and_apex_restoration.ipynb) を統合し、リークのない本番準拠 OOF に対して **「1 プロンプト＝2 回答抽出 × 300 回モンテカルロ試行」** を標準評価指標とする。
- **タスク 1-2: 後処理パラメータのローカルスイープ**
  - 上記 2-Passage OOF を用い、`balance_logits`（Sinkhorn / 事前分布補正）の強度（`0.30`, `0.20`, `0.15`, `0.00`）および `target_mix`（`0.35`, `0.40`）の感度と 95% 信頼区間を計測する。
  - **採択基準**: 95% 信頼区間の下限がベースラインを上回る（統計的有意差がある）設定のみを Phase 2 へ回す。

---

### Phase 2: 低リスク・堅牢化サブミッション（本日枠 1〜2 回使用）
**目的**: V56-Fix ベースラインを安定化させ、不均等出題に対する過剰バランス補正の悪影響を排除する。

- **実験 S1: クリーンベースライン + 後処理強度緩和 (`strength = 0.15 〜 0.20`)**
  - **構成**: V56-Fix ベース（`Qwen3 0.40`, `WeMM 0.07`, `ATLAS 0.10`, `GSQ 0.03`）に対し、Phase 1 で有意改善が確認された `balance_strength`（例: `0.15` または `0.20`）のみを適用。
  - **リスク**: 推論時間は約 6 時間（9 時間上限に対し安全マージン 3 時間確保）。タイムアウトリスクは極めて低い。
- **実験 S2（選択肢）: 公開 `0.684` 型クリーン構成のベンチマーク**
  - もし Phase 1 の OOF 比較で「WeMM / 兄弟残差を削ぎ落とした公開 `0.684` 型（`comp_stack=0.15` + `Sinkhorn=0.20〜0.30`）」が明確に優位だった場合、その構成を 1 枠投じて自環境での実測値・実行時間を取得する。

---

### Phase 3: 本質的差別化（ボトルネック打破・独自モデルの学習）
**目的**: 公開ウェイトのブレンド（`0.680〜0.684` の天井）を超え、`0.69〜0.70+` を目指すための未公開シグナルを構築する。

- **アプローチ 3-A: クローン 3 クラス特化のリファインヘッド（最優先ターゲット）**
  - **対象**: 激しい混同が確認されている `glm-5.3` / `glm-5.3-flash` / `claude-fable-5`。
  - **手法**:
    1. 公式 `train.csv` および公開拡張データ（`prvsiyan/prvsiyans-extended-name-that-llm-dataset` 等、重複・リーク除外済み）を使用。
    2. この 3 クラスに絞ったデータセットで、**専用分類ヘッド（または軽量 MLP / SVC）** を学習。
    3. 本番推論では、18 クラスアンサンブルの予測確率上位がこれら 3 クラスに集中したサンプルのみを対象に確率を再配分（2 段階カスケード）する。
  - **検証ゲート**: 必ず Phase 1 の 2-Passage OOF で 3 クラス単体の Recall および全体 Balanced Accuracy の有意向上を確認してから提出する。

- **アプローチ 3-B: Qwen3-8B 中間層（Early-Mid Layers）文体プロービング**
  - **仮説**: Transformer 最終層は意味（トピック）に引っ張られるため、同一文体の別モデル分離には第 10〜16 層付近の隠れ状態（トークン生成リズム・語彙選択の癖）が有効に働く可能性がある。
  - **手法**: 既に計算している Qwen3-8B 推論パス内で特定中間層のプーリング特徴を追加抽出し、Linear Head / Ridge で学習・ブレンド（追加推論時間の増加を最小限に抑制）。

- **アプローチ 3-C: 極軽量 N-gram / 句読点統計スタックの独立補完**
  - GPU 時間を一切使わず（CPU 数十秒）、文字 3-5 gram・単語 1-3 gram の TF-IDF + Ridge を微少重み（`0.03〜0.05`）でブレンドし、深層モデルの分散を低減する。

## 3. 運用・リスク管理ルール（Operational Guardrails）

1. **提出前 OOF ゲート（No Blind Submissions）**:
   - 2-Passage Sparse Sampling OOF において「ベースライン比で改善（かつ 95% 信頼区間に改善トレンドがある）」と確認できない変更は、原則として Kaggle 提出枠を消費しない。
2. **単発 LB スコアへの過剰反応の禁止**:
   - 公開 LB に最大 `0.009` の揺れが存在する以上、1 回の提出結果（特に `±0.004` 以内）だけでアーキテクチャを大きく振り回さない。
3. **9 時間タイムアウト防衛（Hard Cap）**:
   - 大規模モデル（14B/27B クラス）の新規追加は行わない。新機能は「推論パイプラインの既存モデルからの特徴再利用」または「CPU/軽量モデルの追加（合計実行時間 +15 分以内）」に限定する。
